# 视频数据 Buffer 流转技术报告

> 主题：ESP32-P4 → Jetson 的 H.264 实时视频链路中，数据从采集、编码、UDP 分片传输、
> 组帧、解码到融合层环形缓冲的完整流转过程。
> 配套代码：
> - 接收/解码端：`/home/rock/photo_receive/esp_udp/h264_video_client.py`
> - 融合层（环形缓冲 + 时间对齐）：`/home/rock/imu_qt_viewer.py`

---

## 1. 总体架构

```
[ESP32-P4 发送端]                                       [Jetson 接收端]
┌─────────────────────────────────────────────┐        ┌─────────────────────────────────────────────────┐
│  摄像头采集(YUV/RGB)                         │        │  UDP 接收线程                                   │
│      │  mmap 共享缓冲 (零拷贝, 见 §3)        │        │      │  recvfrom(), 内核 SO_RCVBUF≈2.85MB          │
│      ▼                                      │        │      ▼                                          │
│  H.264 硬件编码器 (ESP32-P4 硬编)            │        │  组帧器 frame_buffers[seq]                      │
│      │  编码码流环形缓冲 (见 §2 第2层)       │        │      │  FIRST/MIDDLE/LAST 拼包 + 超时/丢包策略      │
│      ▼                                      │        │      ▼                                          │
│  8B 包头 + UDP 分片发送线程                  │        │  H.264 解码器 PyAV CodecContext                 │
│      │  SINGLE / FIRST / MID / LAST          │        │      │  SPS/PPS 注入 + DPB 监控/重建 (§5)           │
│      ▼                                      │        │      ▼                                          │
│  UDP 直连 (局域网, port 1235)               │ ─────► │  显示 + 融合层 RingBuffer(打包存储) (§2 第3层)  │
└─────────────────────────────────────────────┘        └─────────────────────────────────────────────────┘
```

整条链路是**多级生产者-消费者**结构，每一级用**有界缓冲**（mmap 共享缓冲 / 环形缓冲 / 组帧表 /
内核 socket 缓冲）解耦前后两级的速率差异，避免某一级阻塞把延迟传导到整条链路。

## 2. 三层生产者-消费者级联流水线（明确标注）

整条链路可以划分为三级**生产者(P) → 消费者(C)**，每级之间都有一个有界缓冲，形成级联流水线：

| 层级 | 位置 | 生产者 P | 消费者 C | 中间缓冲 | 同步机制 |
|------|------|----------|----------|----------|----------|
| 第 1 层 | 发送端 | 摄像头采集线程 | H.264 硬件编码器 | **mmap 共享缓冲**（多缓冲轮转） | 帧完成信号/信号量 |
| 第 2 层 | 发送端 | H.264 硬件编码器 | UDP 分片发送线程 | **编码码流环形缓冲** | 读写指针 + 条件变量 |
| 第 3 层 | 接收端 | UDP 接收线程 | 组帧器 → 解码器 → 融合层 | SO_RCVBUF + frame_buffers + RingBuffer | 线程锁 + 事件 + 环形缓冲 |

### 2.1 第 1 层：采集 → 硬件编码（发送端）

- **生产者**：摄像头采集线程。CSI/MIPI 摄像头通过 DMA 把一帧 YUV/RGB 直接写入物理内存。
- **消费者**：ESP32-P4 硬件 H.264 编码器，从该内存读取并编码。
- **中间缓冲**：`mmap` 共享缓冲。摄像头 DMA 缓冲经 `mmap` 映射到用户态后，采集和编码
  **共享同一块内存**，采集端写完、编码端直接读，**不产生额外 memcpy**（详见 §3）。
- **流水化**：采用 double/triple buffering，采集写第 N 帧的同时，编码器正在编第 N-1 帧，
  采集与编码并行，把“采集时间 + 编码时间”从串行改为重叠。

### 2.2 第 2 层：硬件编码 → UDP 分片发送（发送端）

- **生产者**：硬件编码器，输出 H.264 NAL 码流（SPS/PPS/IDR/P 帧）。
- **消费者**：UDP 分片发送线程，负责加 8 字节包头、按 `SINGLE/FIRST/MID/LAST` 分片并 `sendto`。
- **中间缓冲**：编码码流**环形缓冲**。编码器是“生产者”写入码流，发送线程是“消费者”读走；
  环形缓冲吸收“编码速率”与“网络发送速率”之间的短时抖动，避免编码器因网络拥塞而停顿。

### 2.3 第 3 层：UDP 接收/组帧 → 解码 → 融合（接收端）

这一层内部又细分为连续的三级消费链（本质上是同一个“接收-解码-消费”流水线）：

- **生产者**：UDP 接收线程，`recvfrom()` 把数据报到用户态。
- **消费者① 组帧器**：`frame_buffers[seq]` 组帧表按 `seq` 暂存分片，`LAST` 包到达后 `b''.join()`
  拼接成完整帧（见 §4）。
- **消费者② 解码器**：PyAV `CodecContext` 逐帧解码，内部维护 DPB（见 §5）。
- **消费者③ 融合/显示层**：解码帧写入 `latest_frame`，并送入 `DataFusionLayer` 的
  `RingBuffer`（图像打包为 JPEG 存储，见 §5 末段）。

> 三层级联的价值：采集、编码、发送、接收、解码五步并行执行，端到端延迟不再等于各步之和，
> 而是由**最慢一级的节拍 + 每级缓冲的排队时间**决定，从而把总延迟压到 30ms 以内（见 §6）。

## 3. mmap 零拷贝的具体位置

`mmap` 零拷贝用于**发送端采集缓冲与编码器输入之间**，是链路中数据量最大、最值得省拷贝的一环。

### 3.1 采集缓冲 ↔ 编码器输入（发送端，核心零拷贝点）

```
摄像头 DMA ──写入──► 物理内存(帧缓冲) ◄──mmap── 用户态虚拟地址
                          ▲
                          └── H.264 硬件编码器直接读同一块内存，免 memcpy
```

- 摄像头通过 DMA 把一帧 YUV/RGB 写入物理内存；
- 通过 V4L2 `VIDIOC_REQBUFS` + `mmap()` 把该物理内存映射到用户态虚拟地址；
- 硬件编码器**直接引用这块 mmap 地址**进行编码，**跳过“内核缓冲 → 用户缓冲”的一次拷贝**。

### 3.2 编码输出 ↔ UDP 发送（发送端，可选的第二处零拷贝）

若编码器把码流写入 `mmap` 共享缓冲，UDP 发送线程直接读该共享缓冲、只在其上加 8B 包头后发送，
则编码输出到发送之间同样**免拷贝**；否则用环形缓冲 + 指针搬运（一次拷贝）。

### 3.3 接收端：如何尽量减少拷贝

Python 接收端（`h264_video_client.py`）无法用 mmap 直接拿内核 socket 缓冲，但通过以下方式减少拷贝：

1. 调大内核接收缓冲 `SO_RCVBUF`（≈2.85MB），平滑突发流量，避免丢包后重传（UDP 无重传，只能靠大缓冲）。
2. `recvfrom()` 直接落到用户态 `data`，后续 `parse_udp_header` 只做切片 `data[8:]`（`bytes` 切片是引用，不拷贝）。
3. 组帧时 `b''.join(chunks)` 只发生一次拼接拷贝（不可避免的组装成本）。
4. 解码输出 `latest_frame` 只保存引用，显示/融合线程不深拷贝。
5. 融合层 `push_image` 直接把帧引用写入环形缓冲，仅在 `pack_image()` 做 JPEG 压缩时才产生新缓冲。
6. 若要接收端也做到真·零拷贝，可换用 **Jetson NVDEC 硬解 + DMA/V4L2 输出**，解码帧直接落 mmap 内存。

## 4. 自定义 UDP 传输协议

### 4.1 8 字节包头定义

每个 UDP 数据报统一携带 **8 字节大端包头**，之后紧跟负载：

| 字节偏移 | 字段 | 长度 | 含义 |
|---------|------|------|------|
| 0–1 | `seq` | 2B | 帧序号（0–65535 循环，大端） |
| 2 | `flags` | 1B | 分包标志 |
| 3 | `pkt_type` | 1B | 包类型 |
| 4–7 | `size` | 4B | 整帧字节数（大端；仅 FIRST/单包携带，其余为 0） |

解码端 `parse_udp_header()`：

```python
seq      = (data[0] << 8) | data[1]
flags    = data[2]
pkt_type = data[3]
size     = (data[4] << 24) | (data[5] << 16) | (data[6] << 8) | data[7]
payload  = data[H264_UDP_HEADER:]          # data[8:]
```

### 4.2 分包标志 `flags`

| 值 | 名称 | 语义 |
|----|------|------|
| `0x03` | `SINGLE` | 单包帧：整帧 ≤1452B，一个包直接解码 |
| `0x00` | `FIRST` | 多包首包：携带整帧 `size`，创建组帧条目 |
| `0x01` | `MIDDLE` | 中间包：追加负载 |
| `0x02` | `LAST` | 尾包：标记完成，触发组帧 |

### 4.3 包类型 `pkt_type`

| 值 | 名称 | 语义 |
|----|------|------|
| `0x00` | `VIDEO` | 视频帧数据 |
| `0x01` | `SPSPPS` | 独立 SPS/PPS 参数集包（定期下发） |
| `0xFE` | `READY` | ESP32 就绪信号（握手） |
| `0xFD` | `ACK` | PC 确认信号（握手） |

### 4.4 单包帧与多包分片

- **单包帧**（`flags == SINGLE`）：帧数据 ≤ 1452B（`UDP_MTU - 8`），收到即送入解码器。
- **多包分片**（`FIRST/MIDDLE/LAST`）：
  1. `FIRST` 包在 `frame_buffers[seq]` 创建条目，记录 `expected_size`（整帧大小）、
     `first_time`（首包到达时间）、`chunks`、`received_bytes`、`flags_seen`。
  2. `MIDDLE`/`LAST` 追加到 `chunks`。
  3. `LAST` 包置 `complete=True`，随后按 `chunks` 索引排序、`b''.join()` 拼接成完整帧，
     立即送入解码器。

### 4.5 分片超时组装 + P 帧丢弃策略（保护参考帧质量）

组帧监控线程每 **100ms** 巡检未完成帧（`frame_assembly_timeout = 0.5s`）：

1. 用 `FIRST` 包的 `size` 精确计算期望分片数：
   `expected_chunks = ceil(expected_size / 1452)`，并计算 `received_pct = received_bytes / expected_size`。
2. **已收 ≥95%**：判定为尾部少量丢包，强制完成该帧。
   - 若是 **IDR 帧**：先 `flush()` 解码器清空损坏 DPB，再解码（干净重启）。
   - 若是 **P 帧**：**直接丢弃**，避免损坏 P 帧污染 DPB 引发后续 P 帧连锁花屏。
3. **已收 <95%**：直接丢弃，不把半帧送入解码器。
4. 无 `expected_size`（旧固件）时回退到分片数阈值判断（≥30 片强制完成）。

> 设计目标：丢包只丢“一帧/一个 GOP”，绝不让损坏参考帧进入 DPB 造成级联花屏。

## 5. H.264 压缩、SPS/PPS 缓存与 DPB 监控重建

### 5.1 H.264 压缩（约 30 倍）

原始 YUV420 一帧约 `W×H×1.5` 字节，H.264 以 I/P 帧预测 + 熵编码 + 量化压缩，
典型码流可把原始 YUV 压到 **约 1/20 ~ 1/50**，本项目取 **约 30 倍** 的工程口径
（具体倍率取决于分辨率、量化参数 QP 与画面复杂度）。以 800×1280、25fps 为例，
单帧码流约 184KB，码率约 4.6MB/s，可稳定跑在局域网 UDP 上。

### 5.2 SPS/PPS 参数集缓存（发送端 + 接收端）

- **发送端**：缓存 SPS/PPS 参数集，并以 `pkt_type = SPSPPS` 的独立包**周期性下发**，
  使迟加入或丢包后的接收端能重新拿到参数集。
- **接收端**：`_extract_sps_pps()` 从首个完整 IDR 帧里提取 SPS(type 7) / PPS(type 8) 并缓存
  `cached_sps_pps`；同时缓存周期性下发的 SPSPPS 独立包。
- **注入策略** `_ensure_sps_pps()`：当 UDP 丢包导致某 IDR 帧缺少 SPS/PPS 时，把缓存的参数集
  注入到该 IDR 帧前再解码；**只对 IDR 注入，不给 P 帧重复注入**，避免反复刷新解码器状态。

### 5.3 DPB 解码缓冲区监控 + 解码器重建

- 维护 `consecutive_decode_failures`，成功解码清零，失败累加；阈值 `max_consecutive_failures = 10`。
- **轻度故障**（`_decode_frame_direct`）：连续失败 ≥10 次 → `decoder.flush()` 刷新 DPB。
- **重度故障**（`process_frame`）：连续失败 ≥10 次 → `decoder.reinit()` **重建解码器实例**，
  并置 `_waiting_for_idr = True`，**丢弃所有 P 帧直到下一个 IDR**。
- 为什么需要 `_waiting_for_idr`：解码器重建后 DPB 为空，P 帧因缺少参考帧会反复失败并触发
  再次重建，形成死循环；只有不依赖参考帧的 IDR 才能让解码器干净恢复。

### 5.4 流式 H.264 解码（接收端）

采用 PyAV `CodecContext` **逐访问单元流式解码**：每帧数据（SPS/PPS + IDR 切片 或 P 切片）
作为一个完整访问单元送入解码器，解码器内部维护 DPB 自动管理 IDR/P 参考关系，无需外部累积
缓冲或 GOP 扫描；配合 §5.2/§5.3 的 SPS/PPS 注入与 DPB 重建，实现丢包后快速恢复。

## 6. 端到端延迟预算（< 30ms）

在“采集/编码/发送/接收/解码”五级流水并行 + mmap 零拷贝 + 硬件编码 + UDP 直连的前提下，
单帧端到端延迟主要由**最慢一级节拍 + 各级缓冲排队**决定，典型预算如下：

| 环节 | 手段 | 典型耗时 |
|------|------|----------|
| 摄像头曝光/读出 | CSI/MIPI DMA 直接落内存 | 3–5 ms |
| H.264 编码 | ESP32-P4 硬件编码器 | 2–5 ms |
| 采集→编码搬运 | mmap 零拷贝 | ≈0 ms |
| UDP 分片 + 发送 | DMA/网卡 + 小分片 | 1–3 ms |
| 网络传输 | 局域网直连（有线/低干扰） | <1–2 ms |
| UDP 接收 + 组帧 | 大 SO_RCVBUF + LAST 即拼 | 2–5 ms |
| H.264 解码 | PyAV 软解（可选 NVDEC 硬解） | 3–8 ms |
| 显示/融合层写入 | 引用传递写 RingBuffer | <1 ms |
| **合计** | | **≈12–28 ms < 30ms** |

> 说明：30ms 为**设计目标**，实际值随分辨率、帧率、QP、网络抖动而变化；I 帧（IDR）因体积大，
> 其发送/解码耗时会高于 P 帧，属正常波动。

## 8. 结论

本方案通过 **自定义 8B UDP 分片协议 + 分片超时/P 帧丢弃** 保障丢包下的参考帧质量，
通过 **三层生产者-消费者级联 + mmap 零拷贝 + 硬件编码 + UDP 直连** 将端到端延迟控制在 30ms 内，
通过 **H.264 压缩 + SPS/PPS 缓存 + DPB 监控/解码器重建** 实现丢包后快速恢复的流式解码，
最终把解码帧以**打包存储**方式写入 Jetson 端数据融合层的环形缓冲，完成与 IMU/电机的多路时间对齐。
