# 热启动 / 冷启动 实测汇总（2026-10-16）

> ⚠️ 本文档修正一个**测量方法错误**：单次采样不可靠。
> 三次测量结果不一致，只有**重复测量 + 干净状态**的结论可信。

## 一、测量演进（为什么不能看单次）

| # | 时间 | 方法 | 我们 | Ollama | 问题 |
|---|---|---|---|---|---|
| 1 | 12:02 | 各 1~3 次 | 135 / 176ms | 223ms | ⚠️ 单次采样，落到"幸运值" |
| 2 | 12:07 | 各 5 次（非干净态）| 284ms（217-450）| 257ms（200-289）| ⚠️ 我们 slot 有残留 |
| 3 | **12:08** | **重启到干净态，各 8 次** | **中位 210ms** | **中位 203ms** | ✅ **可信** |

## 二、可信结论（第 3 次测量）

**热启动（服务常驻后的单次请求端到端首 token）**

| | 我们（llama.cpp 9B）| Ollama（9B）|
|---|---|---|
| 平均 | 216ms | 201ms |
| **中位** | **210ms** | **203ms** |
| 范围 | 179 ~ 266ms | 189 ~ 208ms |
| 波动 | 较大（±40ms）| 小（±10ms）|

→ **结论：基本持平，Ollama 略快约 3%（差距 <5%）**

这与技术报告 §5.2 的判断一致：**"Ollama 底层也用 llama.cpp，性能差距小（<5%）"**。
单纯比"单次短请求"的 TTFT，我们**不占优势**——因为 prompt 仅 ~10 token，
prefill 几乎不耗时，耗时全在框架调度/SSE/首 token 启动，两家同源内核自然接近。

**冷启动（进程/模型从零加载）**

| 场景 | 我们 | Ollama |
|---|---|---|
| 首次启动（**page cache 冷**，从 eMMC 读 5.8GB）| **26.9s** | 33.5s（加载+CUDA 32.8s）|
| 再次启动（**page cache 热**，从内存读）| **5.5s** | — |
| 冷启动端到端首 token（同口径）| 26.9 + 0.45 ≈ **27.4s** | **33.5s** |

⚠️ **两点必须注意**：
1. **口径**：我们的 26.9s 是"服务就绪"，Ollama 的 33.5s 是"端到端首 token"。
   同口径应为 **27.4s vs 33.5s**（差距 18%），而非 26.9 vs 33.5（20%）
2. **不比引擎**：我们要读的权重是 **5.8GB（q4_k_m）**，Ollama 是 **6.6GB**。
   按磁盘速率折算：我们 5.8GB/26.9s≈216MB/s，Ollama 6.6GB/32.8s≈201MB/s —— **速率接近**。
   所以冷启动更快**主要来自模型更小，而非引擎更优**
3. **page cache 影响巨大**：同一台机器同一模型，冷 cache 26.9s、热 cache 5.5s（差 5 倍）

## 三、那"我们更快"体现在哪？

不在**单次短请求**，而在**长对话 / 多轮上下文**：

| 维度 | 我们 | Ollama |
|---|---|---|
| 50 轮缓存命中率 | **90.9%** | 无对应机制 |
| 100 轮对话 | ✅ 100/100 完成，~1.5s/轮 | ❌ 300s 只跑 20 轮，~15s/轮 |
| 超窗口历史 | ✅ 磁盘 swap + RAG 恢复（0.78s）| ❌ 截断后每轮重新 prefill |
| 200 轮记忆抽查 | ✅ 10/10 正确 | ❌ 答错 |

**一句话**：优势是**"长对话下开销恒定 + 记忆可恢复"**，不是"单次请求更快"。
