# 与 Ollama 对比：三个维度必须分开讲

> 背景：常被混为一谈的三个"优势"其实是**不同性质**的。
> 讲错会被内行质疑，这里逐条分清，并给出经核实的数据。

## 维度一：进程存活策略（常驻 vs 自动卸载）★ 2026-10-16 实测

**实测条件**：同一台 Jetson AGX Orin 64GB，**两边都是 9B**（我们 q4_k_m / Ollama 同规模），
口径统一为**端到端首 token**（发出请求 → 第一个 token 到达）。
脚本：`tools/hotstart_compare.py`，原始输出：`docs/hotstart_measured_20261016.txt`。

| 场景 | 我们（llama.cpp 9B，常驻）| Ollama（9B）|
|---|---|---|
| **冷启动**（加载→首 token）| 服务就绪 **26.9s**；首个请求 TTFT 450ms | **33.5s**（模型加载+CUDA 32.8s + 预填充 0.75s）|
| **热启动 TTFT** | **135ms / 176ms**（第 2、3 次请求）| **223ms**（常驻后）|
| 生成速度 | 22.3 ~ 22.5 tok/s | 同量级 |
| 冷/热差距 | — | **150 倍**（33.5s ÷ 0.223s）|

**结论（数据支撑）**：
- ✅ 我们**始终热启动 135~176ms**——因为服务常驻、mlock 锁定、前缀缓存命中
- ✅ Ollama 空闲卸载后冷启动 **33.5s**（此前记录的 27.1s 与其同量级，属实）
- ✅ **即使两者都处于热态，我们（~152ms）也比 Ollama（223ms）快约 32%**（得益于 64K 池 + 前缀缓存 + 16-slot unified）
- ⚠️ 边界仍成立：Ollama 可配 `OLLAMA_KEEP_ALIVE=-1` 常驻 → 届时其热启动为 223ms，差距缩至 32%（仍非零）

### mlock 的真正作用边界（重要）
- `-lm mlock` **只在进程生命周期内**防止模型/KV 页被换出到 swap（防抖动）
- **不跨进程存活**：一旦进程退出（主动 kill 或被 OOM 杀掉），内存即释放
- 因此 mlock 保障的是 **"常驻期间的稳定性"**，不是"快速重启"
- 实测佐证：我们的**冷启动（26.9s）与 Ollama D冷启动（33.5s）同量级**，都不快——
  优势全部来自"**不卸载**"这个部署选择，而不是"重启更快"


## 维度二：超上下文历史处理（★ 真正的技术差异）

这是**报告 §10.2 实测的 10 倍差距**，也是最有说服力的一条：

| 指标 | 我们（磁盘 swap 恢复） | Ollama（截断后重新计算） |
|---|---|---|
| 100 轮对话 | ✅ **100/100 完成** | ❌ 300s 只跑 20 轮 |
| 每轮耗时 | **~1.5s** | ~15s（**10 倍差距**）|
| 早期记忆 | ✅ 0.78s 恢复 | ❌ 答错（"我是通义千问"）|

**性质：这是实现差异（我们改了代码，Ollama 是封闭二进制）。**
- Ollama 超窗口 → 截断历史 → **每轮重新 prefill 全量上下文** → 轮次越靠后越慢
- 我们 → 历史 swap 到磁盘（gzip）+ RAG 语义检索换入 → 开销恒定且记忆可恢复

## 维度三：前缀缓存（两者都有，不要当独占优势）

| | Ollama | 我们 |
|---|---|---|
| 全局前缀缓存 | ✅ 默认启用（KV q8_0 + flash-attn）| ✅ `--cache-prompt` / `--cache-reuse 256` |
| 实测 | 39.7 tok/s，首 token 92ms | **41.1 tok/s，首 token 81ms**，50 轮命中率 **90.9%** |

**性质：同源技术（Ollama 底层就用 llama.cpp），差距 <5%，不构成宣传点。**

## ❌ 已淘汰的错误说法（不要再用）

| 错误说法 | 问题 |
|---|---|
| "卸载服务后重启动，首 Token 稳定 120-160ms" | **主语反了**：卸载=进程退出，mlock/前缀缓存随之失效；重启必重新加载权重 |
| "相较 Ollama 空闲卸载后的冷启动 27.1s"（作为对比）| **对比不公平**：拿"我们常驻"比"Ollama 卸载"，且未标注 Ollama 可配 `KEEP_ALIVE=-1` |
| "120-160ms / 27.1s" | 报告中**查无此数据**（报告实测为 81ms 首 token）；如确有实测需补记录 |

## ✅ 推荐表述（三选一，按场合）

**A. 讲部署策略（简洁）：**
> llama-server 常驻运行并以 `-lm mlock` 锁定内存，模型与 KV 不被换出、不自动卸载；
> 相比 Ollama 默认空闲 5 分钟卸载模型（再次请求需冷启动重新加载），
> 家网关场景下始终为热启动，首 Token 稳定 ~81ms。

**B. 讲硬实力（推荐，用实测数据）：**
> 超上下文场景下，Ollama 截断历史并每轮重新 prefill，100 轮测试 300s 仅完成 20 轮；
> 我们的磁盘 swap + RAG 恢复方案完成 100/100 轮，每轮 ~1.5s（**快 10 倍**），
> 且早期记忆可恢复（0.78s 找回 6 轮前事实），200 轮后 10/10 抽查正确。

**C. 一句话总结：**
> 优势不在"生而更快"（与 Ollama 差 <5%），而在**长对话下的记忆可恢复 + 开销恒定**。
